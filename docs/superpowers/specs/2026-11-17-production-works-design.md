# Актуализация калькулятора стоимости изделий — дизайн

Дата: 17.11.2026
Статус: source-first реализация и portable-сборка выполнены; React Flow-бандл переиспользован из рабочей копии.

## Намерение

Актуализировать производственные работы калькулятора по `Данные.xlsx`, сохранив текущие пользовательские цены, существующие позиции и расчетную методику. Повторная актуализация должна выполняться тем же подготовительным сценарием, без ручного редактирования сгенерированного Worker.

Главный источник — `calculation data/Данные.xlsx`, лист `Перечень_работ`. Книга `Сметный калькулятор СК-V-3.06.xlsx` используется только для сверки формул и пояснений. Материальные справочники не изменяются.

## Цели

- Проверить все 190 производственных позиций, включая скрытые строки.
- Привести однозначно сопоставленные названия и единицы к первоисточнику.
- Добавить отсутствующие производственные позиции и сохранить позиции, существующие только в калькуляторе.
- Разделить базовую стоимость источника и текущую стоимость строки калькуляции.
- Сохранять исходную формулу, параметры, единицы и пояснение цены без пересчета Excel-формулы в приложении.
- Добавить блок `Ценообразование`, индивидуальный режим цены, сохранение после перезапуска и сброс к базовым значениям.
- Считать нормо-часы по физическому объему только при согласованной производительности и совпадении единиц.
- Сформировать десять структурированных отчетов сверки.

## Не входит в работу

- Изменение исходных XLSX.
- Изменение материальных справочников и связанных с ними каталогов.
- Удаление или архивирование позиций, которых нет в `Данные.xlsx`.
- Автоматическое заполнение неизвестных цен или производительностей.
- Автоматическая конвертация единиц без явного коэффициента.
- Публикация на Sites и изменение удаленной базы.
- Создание импорта Excel внутри пользовательского интерфейса.

## Выбранный подход

Используется source-first подготовительный слой в исходном проекте.

```text
Данные.xlsx + Сметный калькулятор СК-V-3.06.xlsx
  → подготовительный импортёр
  → нормализованный набор производственных работ
  → отчеты сверки
  → обновленный dist/catalog.js
  → изменения расчетной модели и UI
  → node build-worker.cjs
  → node run-checks.cjs
```

Внешняя переносная папка остается артефактом сборки. Редактируются исходники архива `Calculator-source-2026-11-17-153643`, прежде всего `dist/`, `worker/`, `drizzle/` и проверки.

Причина выбора: это единственный вариант, который одновременно дает повторяемость будущих обновлений, сохраняет существующую архитектуру и не переносит сложность XLSX-парсинга в браузер.

## Подготовительный импорт и сопоставление

Создается отдельный скрипт подготовки данных в исходном проекте: `tools/import-production-works.cjs`.

Он:

1. Читает все строки листа `Перечень_работ`, включая скрытые и отфильтрованные записи.
2. Читает исторические формулы, примечания и параметры из вторичной книги только для отчетов и пояснений.
3. Нормализует имя для поиска по регистру, пробелам, пунктуации и техническим сокращениям.
4. Сопоставляет только записи `kind=work` и не затрагивает материалные листы.
5. При однозначном совпадении записывает канонические имя и единицу из `Данные.xlsx`.
6. Добавляет отсутствующие работы в существующие категории.
7. Сохраняет калькуляторные работы без совпадения.
8. Объединяет дубликаты только при совпадении категории, единицы и формулы стоимости; остальные оставляет отдельными.
9. Не заменяет существующую числовую текущую цену при первоначальном импорте.
10. Считает ноль, текст и пустое значение отсутствующей ценой; неизвестное остается `null`.
11. Записывает базовые значения и исходные параметры в каталог и готовит отчеты.

Парсер XLSX выбирается как dev-only инструмент подготовки. Runtime-приложение не получает зависимость от загрузки Excel и не меняет пользовательский UI.

Канонический артефакт каталога остается `dist/catalog.js`: импортёр обновляет только производственные записи, сохраняя материалные записи и структуру каталога.

## Модель данных

Существующее поле `price` сохраняется как текущая стоимость для обратной совместимости. Добавляются необязательные поля:

```text
basePrice             базовая цена из Данные.xlsx
pricingMode           calculated | individual
baseUnit              каноническая единица из источника
sourceFormula         текст формулы или пояснение формирования стоимости
sourceParameters      числовые параметры и единицы исходной формулы
sourceFinalCost       сохраненная итоговая стоимость источника
physicalQuantity      вводимый физический объем
physicalUnit         единица физического объема
productivity          количество физического объема за 1 н/ч
productivityUnit      единица производительности
productivityStatus    approved | candidate | conflict | missing | not_applicable
unitChangeNotice      уведомление о синхронизации единицы
```

Старые JSON без этих полей продолжают проходить валидацию. Для старых строк `basePrice` при открытии не выдумывается: поле остается `null`, пока строка не будет сопоставлена с источником.

## Ценообразование и единицы

- При добавлении из каталога `basePrice` и `price` первоначально равны достоверной цене источника.
- Ручное изменение `price` переводит строку в `pricingMode=individual`; `basePrice` не меняется.
- При последующей актуализации базовая цена, формула, параметры и базовая единица обновляются из источника.
- Текущая цена обновляется только для режима `calculated`; индивидуальная цена сохраняется.
- При изменении базовой единицы текущая цена остается прежней, `unitChangeNotice` сохраняется до следующего сохранения конфигурации.
- Кнопка `Сброс стоимости к базовым значениям` возвращает последнюю базовую цену, единицу, формулу и параметры и переводит строку в `calculated`.
- В интерфейсе деньги показываются с двумя знаками, расчеты хранят полную точность.

## Нормо-часы

Импорт создает сведения о производительности для 50 позиций с заполненными `H/I`.

- 20 позиций из списка конфликтов получают статус `conflict` и не запускают автоматический расчет.
- Согласованные позиции получают статус `approved`.
- 20 позиций без производительности получают статус `missing` и разрешают ручной ввод нормо-часов.
- 35 позиций со значением `L`, но единицей стоимости не `н/ч`, получают статус `not_applicable` и не интерпретируются автоматически.

Для `approved` при наличии физического объема и совпадении единиц:

```text
calculatedNh = physicalQuantity / productivity
operationCost = calculatedNh * currentPrice
```

Промежуточное округление не выполняется. Отрицательный физический объем отклоняется. Нулевая или отсутствующая производительность отключает автоматический расчет. При отсутствии нормы пользователь может ввести количество `н/ч` вручную.

Текущий расчетный движок продолжает работать для строк, где объем уже задан в единице ставки. Новая ветка применяется только к строкам с валидным статусом производительности.

## Интерфейс

В существующем модальном окне `Настройка позиции`, сразу под полем цены, добавляется неинтерактивный `details`-блок `Ценообразование`.

Он показывает:

- текстовое объяснение;
- формулу или сохраненное пояснение;
- фактические параметры источника;
- единицы измерения;
- производительность и ее статус, если она есть;
- сообщение `Стоимость за ед. указана индивидуально` для индивидуальной цены.

В этой же форме размещаются физический объем, единица, производительность и расчетное количество нормо-часов. Расчетное количество доступно только для чтения; при отсутствии нормы появляется поле ручного ввода.

## Отчеты

Импорт создает в `reports/production-works/` десять JSON-файлов с точными именами из ТЗ:

- `Отчет_сверки_наименований.json`
- `Отчет_расхождений_стоимостей.json`
- `Отчет_отсутствующих_стоимостей.json`
- `Отчет_измененных_единиц_измерения.json`
- `Отчет_добавленных_позиций.json`
- `Отчет_дубликатов.json`
- `Отчет_формул_ценообразования.json`
- `Отчет_нормативов_производительности.json`
- `Отчет_спорных_нормативов.json`
- `Отчет_позиций_без_норм_выработки.json`

Каждая запись проблемы содержит номер источника, имя, категорию, текущее значение калькулятора, значение первоисточника, причину, действие и статус согласования.

## Затрагиваемые исходники

- `tools/import-production-works.cjs` — чтение книг, сопоставление, артефакт каталога и отчеты;
- `dist/catalog.js` — обновленный каталог производственных работ;
- `dist/app.js` — модель строки, редактор позиции, UI блока и reset;
- `dist/domain-schema.js` — проверка новых полей и старых JSON;
- `dist/engine.js` — расчет нормо-часов и использование текущей цены;
- `dist/review-core.js`, `dist/review-ui.js` — сохранение новых полей, подписи и очистка копий;
- `dist/internal-report.js`, `dist/internal-report-ui.js` — вывод источника, режима цены и норм;
- `dist/style.css` или `dist/workspace.css` — минимальные стили блока;
- `tests/` и новые проверки импортера/расчета/UI;
- `build-worker.cjs` и `build-portable.cjs` используются без изменения логики сборки;
- `worker/` и `drizzle/` меняются только если существующей синхронизации строк расчета будет недостаточно.

## Дополнение: цеха и порядок строк в «Изготовлении»

В разделе `3 · Изготовление` список работ отображается группами с фиксированным порядком:

1. `ЧПУ цех`
2. `Металлоцех`
3. `Древообработка`
4. `Лакокрасочный`
5. `Сборочный`
6. `Подрядные`

Для каждой производственной строки добавляется поле `workshop`. Классификация выполняется при импорте и сохраняется в строке:

- `Подрядные` имеет приоритет, если `Тип работ` в первоисточнике содержит `Подрядчик`/`Подрядные`;
- `ЧПУ цех` — явные признаки ЧПУ и станочной обработки: лазер, плазма, гидроабразив, фрезерование, листогиб, вальцовка и аналогичные записи;
- `Металлоцех` — металлообработка, сварка, слесарные работы, зачистка металла, дробеструй, цинкование и другие операции по металлу, не попавшие в ЧПУ;
- `Древообработка` — работы по дереву, доске, фанере, бревну, пиломатериалам и брашировке;
- `Лакокрасочный` — окраска, грунтование, лакирование, покрытия и порошковая окраска;
- `Сборочный` — сборка, упаковка, электромонтаж, петли и прочие операции без более точного признака.

Правила применяются в указанном порядке. Для строк, попавших в fallback `Сборочный`, сохраняется источник классификации и формируется отчет для ручной проверки; автоматического удаления или изменения исходной категории нет.

Внутри каждой группы пользователь меняет вертикальный порядок перетаскиванием строки за рукоятку из трех полосок слева от названия. Перемещение меняет только порядок строк внутри текущего цеха, сохраняется сразу после отпускания в JSON/localStorage и переносится в версии изделия. Для совместимости старых расчетов порядок по умолчанию определяется текущим порядком `state.lines`, после первого изменения записывается `productionOrder`. Стрелки вверх/вниз в интерфейсе не используются.

Группы и порядок не влияют на стоимость, формулы, нормы, базовые/индивидуальные цены или клиентский экспорт. Они меняют только представление производственных работ и внутреннюю детализацию.

## Приемка и проверки

До сборки должны пройти:

- проверка 190 строк источника, включая скрытые;
- проверка совпадения канонических имен и единиц;
- проверка сохранения числовой текущей цены;
- проверка режима individual после перезапуска и актуализации;
- проверка reset к последней базовой цене;
- проверка уведомления при смене единицы;
- проверка группировки по шести цехам и приоритета `Подрядные`;
- проверка перемещения строки вверх/вниз внутри цеха и сохранения порядка после перезапуска/экспорта;
- контрольный пример `18 м2 / 4.5 м2 за н/ч = 4 н/ч`;
- отрицательный объем, нулевая производительность и несовпадение единиц;
- отсутствие автоматического применения 20 конфликтных и 35 дополнительных норм;
- существующие профильные проверки и полный `node run-checks.cjs`;
- `node build-worker.cjs` и, после согласования, `node build-portable.cjs`.

Исходные Excel не изменяются. Публикационные скрипты не запускаются.

## Открытые решения для реализации

- точный dev-only XLSX-парсер и формат временного нормализованного набора;
- способ размещения рабочей копии архива исходников в текущем writable checkout;
- необходимость отдельной SQL-миграции после проверки фактического пути хранения строк.

Эти решения не меняют выбранный подход и могут быть уточнены исполнителем перед написанием кода.
