НОДОВЫЙ РЕДАКТОР · 03.11.2026 · КОРНЕВАЯ РАБОЧАЯ КОПИЯ
process-graph-core.js — CommonJS/браузерное ядро физических характеристик, проверки структуры связей и вычисления зависимых объёмов без DOM и без изменения исходной калькуляции. Модель представляет направленный ациклический граф: один вход и произвольное число выходов. Сборочные узлы с суммированием входов пока не поддерживаются.
Необязательные поля строки: processKey (стабильный ключ, независимый от id строки), processPosition={x,y}, processMetrics={unit,source,area?,faceArea?,length?,mass?,count?,volume?}, processBinding={from,metric,mode:'direct'|'norm',factor,unit,note}. Геометрические значения относятся к одной единице материала; null — неизвестно, 0 — явный ноль. Прямой перенос допускает только одинаковые нормализованные единицы и factor=1. Норма — явное положительное количество единиц процесса на единицу физической характеристики. Данные справочника копируются при первом включении узла и требуют проверки; смена единицы делает прежнюю копию неприменимой.
resolve(calculation,q) возвращает временную калькуляцию и ошибки. Физический объём партии = характеристика × чистый qty материала × (scope=batch ? 1 : q). Для процесса на изделие делится на q; для процесса на партию — нет. Тарифные/машинные операции всегда получают объём на изделие. По цепочке передаётся геометрия исходного материала, а не собственный расход предыдущей операции. Закупочный запас, кратность, минимум и подготовка не входят в передаваемую физическую величину.
engine.js применяет resolve для cost-v1; review-core.js — до разделения строк на обычные затраты и готовые клиентские цены. Повторный проход идемпотентен: у временных строк processBinding снят, processSourceKey сохраняет различие одинаковых процессов для разных источников. Согласование проверяется по исходной калькуляции, не по временным строкам. Старые калькуляции без связей сохраняют прежние суммы и методики. Неизвестные источники/единицы дают ошибку и null вместо старого ручного объёма.
domain-schema.js вызывает валидацию графа до импорта; отсутствие источника допускается как исправимый пропуск, циклы и повторные processKey — нет. business.js сохраняет поля и стабильные ключи при замене id строк в копиях. Проверка монтажной спецификации использует вычисленные объёмы. processPosition исключён из подписей согласования и архива; перенос узла не меняет статус и сохранённый результат. Содержательные изменения связей/геометрии входят в подпись.
process-graph.js/.css — раздел 20, перетаскивание, масштаб, порты, настройка через формы, ручные координаты и возврат к ручному объёму. Процессные поля и внутренние нормы не добавлены в клиентский whitelist. Ядро встроено в общий Worker вместе со схемой; SQL-коллекции и миграции не менялись. PWA включает новые ресурсы через сборку.
Калькуляции с узлами получают version=2/schemaVersion=2 при открытии схемы или очистке копии. DomainSchema принимает форматы 1 и 2; прежнее приложение, принимающее только version=1, отклонит новый файл вместо молчаливого удаления связей и пересчёта по старым ручным объёмам. 2. СТАВКИ
Основной рабочий справочник: izdelie-operation-rates-v2, полный набор ставок.
izdelie-operation-rates-v1 читается при миграции; прежние изменения сохраняются.

В копию операции включаются цена, происхождение, ревизия ставки и условия: марка, толщина, оборудование, качество и единица. Ручное изменение числовых ставок отмечается rateProfile.modified.
Подготовка/минимум/дополнительные расходники при отсутствии поля в старом файле нормализуются в 0; явно заданное null остаётся неизвестным значением и проверяется. Основная цена никогда не превращается из null в 0.
При конфликте разных ставок сохраняются обе версии, местная получает новый код и отметку конфликта. Одинаковые по содержимому ставки не дублируются.

3. СЕРВЕРНОЕ ХРАНЕНИЕ
Миграции: 0000_cloud_storage.sql, затем 0001_record_storage.sql.
entity_records: collection, entity_id, payload, rev, updated_at. Изделие, КП, вариант, ставка и запись справочника имеют отдельный контроль версии. Версии одного изделия пока хранятся внутри записи изделия.
GET /api/records возвращает данные и версии записей; PUT принимает только изменённые записи. Клиент отправляет до 25 записей в транзакции, при большом импорте — несколько транзакций. Каждая транзакция атомарна; весь большой импорт не является одной транзакцией.
Правки разных записей не конфликтуют. Правка той же записи со старой ревизией получает 409. Служебный guard исключает частичное применение транзакции и гонку при проверке ревизий.
Глобальная ревизия остаётся информационным номером состояния. app_state после миграции хранит прежний payload для совместимости/восстановления и номер состояния; рабочие данные читаются из entity_records. При каждом сохранении общий JSON заново не записывается.
Ограничение 1,5 МБ относится к одному запросу, а не ко всей базе. Одна очень большая запись изделия с многочисленными версиями может потребовать дальнейшего разделения версий.
Ежедневная копия содержит фактическое предыдущее состояние записей, включая полный рабочий справочник ставок. Старый PUT /api/state блокируется после миграции; GET остаётся доступным для совместимости.
Приватный доступ по-прежнему обеспечивает Sites. Новые роли и пользователи в эту правку не включены.

4. ВОССТАНОВЛЕНИЕ
Данные проверяются до изменения localStorage. Перед объединением создаётся восстановительная копия. При ошибке записи прежние значения восстанавливаются; вновь созданные ключи удаляются.
Клиентский документ КП содержит только разрешённые поля и хранится отдельно от редактируемой калькуляции.
Старые версии без архива продолжают использовать не изменённую методику cost-v1. Новые сохранения получают снимок результата; неизвестную методику пересчитывать нельзя.
Рабочий расчёт и черновики остаются на устройстве, как и раньше; сохранённые изделия, КП и справочники синхронизируются.
